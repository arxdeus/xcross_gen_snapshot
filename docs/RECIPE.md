- Unique key = engine hash (one compiler per engine; the engine pins exactly one Dart revision). In a user's Flutter SDK: `$FLUTTER_ROOT/bin/internal/engine.version` (engine) and `$FLUTTER_ROOT/bin/cache/dart-sdk/revision` (Dart).
- gen_snapshot rejects kernels from another Dart revision ("Invalid SDK hash", runtime/vm/kernel_binary.cc), the engine rejects snapshots with another md5 snapshot hash / features string. So: exactly one compiler per engine and mode.

## Byte-identity proof (Flutter 3.47.0)
- Official macOS `ios-release/gen_snapshot_arm64` and `ios-profile/gen_snapshot_arm64` were reproduced from source:
  - macOS arm64 host, release: App + app.o identical.
  - macOS arm64 host, profile: App + app.o identical (sha256 of App 267f585b...).
  - Linux arm64 host, release: App identical; app.o differs only in DWARF DW_AT_producer string naming the host.
  - Linux x64 host (cross-compiled, run under emulation), release: App identical.
- IMPORTANT for any comparison: gen_snapshot embeds the `--macho-object` path as an N_OSO stab string in the unstripped App. Always run reference and candidate with the SAME relative output names (`--macho=App --macho-object=app.o` in their own directories) or the string table length differs.
- Without the sort patch a glibc-hosted compiler produces a valid but different snapshot (3.3M bytes differ): libc qsort tie order. The patch ports Apple Libc stdlib/FreeBSD/qsort.c + heapsort.c (BSD-3) into runtime/platform/xcross_apple_sort.h and makes GrowableArray::Sort use it. The heapsort fallback is hit in 37,653 of 45,871 calls, so heapsort must be ported exactly.

## Patch
`dart_sdk.patch` (4 files, applies with `git apply` to a sparse checkout at da6595cd):
- runtime/runtime_args.gni: `dart_xcross_target_os_ios = false` declared arg.
- runtime/BUILD.gn: `dart_os_config` emits DART_TARGET_OS_MACOS + DART_TARGET_OS_MACOS_IOS when the arg is true, while target_os stays the host OS (host toolchain builds gen_snapshot, no Xcode/iOS SDK lookup).

- Run `python3 tools/generate_sdk_version_file.py` (creates sdk/version).
- DEPS-pinned deps (read revisions from that Dart revision's DEPS; fetch with gitiles `<url>/+archive/<rev>.tar.gz`, plain HTTPS):

  - third_party/boringssl/src <- boringssl.googlesource.com/boringssl.git @ boringssl_rev

  - third_party/perfetto/src <- chromium.googlesource.com/external/github.com/google/perfetto @ perfetto_rev (needed for profile; harmless for release)
- Tools from CIPD over plain HTTPS: `https://chrome-infra-packages.appspot.com/dl/<package>/+/<version>` redirects to a content-addressed zip (store/SHA256/<sha>):
  - clang: fuchsia/third_party/clang/{linux-amd64,linux-arm64,windows-amd64} @ clang_version from DEPS -> buildtools/<host>-<cpu>/clang (Dart's GN reads buildtools/<host>/clang/.versions/clang.cipd_version JSON {"package_name","instance_id"}; write it).

  - ninja: infra/3pp/tools/ninja/<platform> @ ninja_tag.

- Windows (implemented in lib/src/build.dart, verified in CI on windows-2022 and windows-11-arm):
  - Toolchain: clang-cl/lld-link from CIPD `fuchsia/third_party/clang/windows-amd64` at `buildtools/win-x64/clang` (GN's default `clang_base_path`, also on arm64 hosts where it runs under x64 emulation; there is no windows-arm64 clang package). gn: `gn/gn/windows-amd64` (no arm64 package; emulated). ninja: `infra/3pp/tools/ninja/windows-<amd64|arm64>` (native).
  - Headers/libs from the installed Visual Studio + Windows SDK 10.0.26100.0 via `build/toolchain/win/setup_toolchain.py` (vcvarsall). Env: `DEPOT_TOOLS_WIN_TOOLCHAIN=0`, `GYP_MSVS_OVERRIDE_PATH=<vswhere -latest installationPath>`, `vs2022_install=<same>` (vs_toolchain.py only knows VS 2017-2022 by year; windows-11-arm ships VS 2026 at `...\Microsoft Visual Studio\18\Enterprise`).
  - `target_cpu == host_cpu` on both hosts, so setup_toolchain.py runs vcvarsall with `amd64` (x64) or `amd64_arm64` (arm64: x64-hosted MSVC tools targeting arm64).   - `patches/windows_host.patch` (1 hunk, build/vs_toolchain.py): `copy_dlls` (run by GN for the default toolchain) copies the VC++ runtime DLLs and on arm64 looks for `Microsoft.VC143.CRT`, which VS 2026 only ships as `VC145`. gen_snapshot links the CRT statically (`/MT`), so missing runtime DLLs are skipped instead of failing `gn gen`.
  - The Dart checkout is done with `core.autocrlf=false` (Windows runners default to true): sources hashed into the snapshot version (tools/make_version.py) must keep LF bytes.
  - Short work dir (`C:/xgs`) to stay under MAX_PATH.

## Windows: argument evaluation order (verified)
- MSVC-ABI compilers (clang-cl included) evaluate function arguments right to left; clang on macOS/Linux evaluates them left to right. Two places in the Dart compiler call `GetNextDeoptId()` twice in one argument list (`FlowGraphBuilder::Suspend` in runtime/vm/compiler/frontend/kernel_to_il.cc and the inliner's artificial branch in runtime/vm/compiler/frontend/flow_graph_builder.cc), so a Windows-hosted compiler swapped the two deopt ids. The suspend point's yield index is its deopt id, so 11 bytes of `PcDescriptors` differed in 6 async functions (found by mapping the differing `__const` bytes to objects with `--write-v8-snapshot-profile-to`). `patches/dart_sdk.patch` hoists both calls into ordered locals; the macOS build with the patch still reproduces the official App byte-for-byte.
